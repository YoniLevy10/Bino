# BINO 2.0 — תקציר לאישור הנהלה

**נושא:** הרחבת BINO להנהלת חשבונות בניין, תקציב, חתימות/החלטות, חיבור בנק, דוחות מעוצבים ואוטומציית רבעון — **בתוספת מסלול מקביל:** Speed Insights P0 + זיכרון אנשי מקצוע (השראת OPC)  
**מקור:** פגישה עם לקוח קיים + סקירת קוד/DB + תוכנית `Israel Speed Insights P0`  
**תאריך:** 16.11.2026  
**סטטוס:** אישור הנהלה התקבל — ביצוע מדורג לפי המלצות ארכיטקט; מסלול Perf/Pros ב־PRs נפרדים  
**ראה גם:** [`BINO_FINANCE_ARCHITECT_RECOMMENDATIONS_HE.md`](./BINO_FINANCE_ARCHITECT_RECOMMENDATIONS_HE.md) · [`BINO_OPEN_SOURCE_RESEARCH.md`](./BINO_OPEN_SOURCE_RESEARCH.md) · [`BINO_COLOR_PALETTE_V2.md`](./BINO_COLOR_PALETTE_V2.md) · [`BINO_FINANCE_ROADMAP.md`](./BINO_FINANCE_ROADMAP.md)  
**עקרון מוצר:** Simple Outside, Powerful Inside

## 1. למה זה חשוב

BINO היום חזקה בניהול תפעולי (קריאות, WhatsApp, דיירים) ובגבייה דרך Grow.  
הלקוח ביקש להפוך כל בניין ל**יחידה פיננסית וניהולית עצמאית** — הנהלת חשבונות, תקציב, שקיפות לדיירים, החלטות עם חתימות, ודוחות ברמת OPC.

זה משנה את ערך המוצר מול חברות ניהול: לא רק תיעוד תקלות, אלא **שליטה בכסף, בתקציב ובהחלטות הבניין** — ומחזק את מדד עלות התחזוקה לבניין והוכחת חיסכון.

## 3. נקודות הפגישה — הרחבה להחלטה

### 3.1 גבייה

**דרישת לקוח:** להמשיך ולחזק גבייה כחלק מהמערכת הפיננסית.

**הצעת מוצר:**
- שימור Grow כמנוע גבייה פעיל (קישורים, ארנק, webhooks, קבלות/חשבוניות מ־Grow).
- חיבור דוחות גבייה להתאמות מול תנועות בנק (הפקדות ↔ חיובים).
- שכבת `PaymentProvider` פנימית לעתיד (בלי להחליף Grow עכשיו).

**סיכון אם נוגעים בלי זהירות:** כפילויות תשלום, סטטוס שגוי, כסף למסוחר לא נכון.

**סטטוס:** Existing → לשמר ולהרחיב דיווח.

### 3.2 הנהלת חשבונות לבניין (דגש מרכזי)

**דרישת לקוח:** הנהלת חשבונות יכולה לשנות לגמרי את הצעת הערך ללקוחות.

**הצעת מוצר — מרכז פיננסי לבניין:**
- יתרת פתיחה/סגירה לתקופה
- סך הכנסות והוצאות
- חיובים שהופקו / שנגבו / חובות פתוחים
- **הפרדה ברורה:** יתרת ספרים ≠ יתרת בנק ≠ תזרים חזוי ≠ כסף שהתקבל בפועל
- רישום הוצאות לפי קטגוריה (ניקיון, חשמל, מעליות, גינון, ביטוח, תיקונים, ספקים, ניהול, חריגות…)
- שיוך לבניין + ספק + אסמכתא + סעיף תקציבי + סטטוס תשלום
- כרטסת דייר/יחידה (כבר יש בסיס) כולל חילופי מחזיקים והיסטוריה על היחידה
- אין מחיקת רשומה שאושרה — רק תנועות מתקנות + Audit Trail

**סטטוס:** Missing (כרטסת גבייה Partial).

**עדיפות:** P0 — ליבת ה־ROI.

### 3.3 ניהול תקציב בניין

**דרישת לקוח:** יצירת ניהול תקציב בניין.

**הצעת מוצר:**
- תקציב שנתי/תקופתי עם קטגוריות וחלוקה חודשית/רבעונית

**דוגמה מה־PRD:** תקציב ניקיון 24,000 ₪; עד סוף רבעון ב׳ הוצאו 15,000 ₪ → ניצול 62.5% וחריגה מקצב ליניארי של חצי שנה.

**סטטוס:** Missing | **עדיפות:** P0

### 3.4 חתימות והחלטות בבניין (רוב)

**דרישת לקוח:** מערכת חתימות; לכל החלטה בבניין נדרש **רוב**; שליחת קישור לדיירים לחתימה על טופס.

**זרימה מוצעת:**
1. מנהל יוצר הצעת החלטה / טופס לחתימה  
2. מגדיר זכאים (בדרך כלל בעלי דירות) וסף (ברירת מחדל **רוב**)  
3. המערכת שולחת **קישור ייחודי** ב־WhatsApp / SMS / אימייל (תשתיות קיימות ב־BINO)  
4. הדייר נכנס מהקישור, מזדהה, חותם (ציור/הקלדה) או מצביע  
5. מעקב חי באחוזים; כשמגיעים לרוב — פרוטוקול + שמירה בספר החלטות  
6. אופציה נפרדת: חתימה על מסמך PDF (לא רק “בעד/נגד”)

**חשוב משפטית (לאישור הנהלה):**
- **רוב** הוא ברירת המחדל המוצרית הפשוטה (יותר ממחצית לפי בסיס החישוב שהוגדר להחלטה).
- אפשרות לכללי רוב מיוחדים בהמשך — בלי לסבך את ה־MVP.
- המערכת לא תציג “החלטה תקפה משפטית” כשיש אי־בהירות.

**פתרון טכני מומלץ (Open Source):**

| גישה | מה זה | המלצה |
|------|--------|--------|
| A. מודול קישור־חתימה בתוך BINO | טוקן + דף חתימה + audit + ספירת % | **Integrate/Build ל־MVP** — מתאים לזרימת “שולחים לינק לדיירים” |
| B. DocuSeal / OpenSign כשירות נפרד | OSS פופולרי עם שליחת לינק מובנית + API | **Integrate כ־sidecar** אם נדרש חותם PDF חזק יותר; רישיון AGPL — **לא** להטמיע בקוד המונולית של BINO |
| C. PaperSign / דומים (MIT) | שירות חתימות קטן יותר | לבדוק בשלות לפני בחירה |

**סטטוס:** Missing | **עדיפות:** P1 (אחרי יסוד פיננסי, או במקביל חלקי)

### 3.7 חיבור לחשבון הבנק — התחלה מ־israeli-bank-scrapers

**דרישת לקוח / הוראת בעלים:** להתחיל מ־[israeli-bank-scrapers](https://github.com/eshaham/israeli-bank-scrapers) — חייבים נקודת התחלה; הדוחות יישענו על נתוני הבנק.

**מה זו החבילה (מאומת מ־GitHub):**
- רישיון **MIT**, כוכבית גבוהה (~1.2k), תמיכה בבנקים מרכזיים בישראל (לאומי, הפועלים, דיסקונט, מזרחי, כאל, מקס, ישראכרט ועוד)
- עובדת עם **שם משתמש + סיסמה** דרך scrapers (דפדפן אוטומטי / Puppeteer)
- מחזירה חשבונות ותנועות לשימוש באפליקציה

**איך זה ייכנס ל־BINO (תכנון):**
1. שכבה פנימית `bank_accounts` + `bank_transactions` פר בניין  
2. ספק ראשון: `IsraeliBankScrapersProvider`  
3. סנכרון מתוזמן + ממשק “חבר חשבון” עם הסכמה מפורשת  
4. מנוע התאמות: הפקדות↔גבייה, תשלומים יוצאים↔הוצאות (בכללי ודאות; מקרים עמומים לבדיקה ידנית)  
5. הדוחות קוראים רק מהשכבה הפנימית — כדי שבעתיד אפשר יהיה להחליף ל־Open Banking מורשה **בלי לשכתב דוחות**

**סיכונים שחייבים אישור הנהלה (לא לטאטא):**

| סיכון | משמעות |
|--------|---------|
| שמירת credentials בנק | דורש הצפנה חזקה, הרשאות, ביטול חיבור, Audit |
| Scraping מול תנאי שימוש של בנקים | סיכון משפטי/תפעולי; UI בנק נשבר לעיתים |
| תשתית ריצה | Puppeteer לא מתאים ל־Vercel Function רגיל — נדרש worker ייעודי |
| לא תחליף לרישיון AIS | זה **פיילוט מהיר לנתונים**; שדרוג ל־Feezback / Open-Finance מתוכנן בהמשך |

**המלצת הנהלה:** לאשר **פיילוט מוגבל** (1–2 בניינים, opt-in, feature flag) על scrapers, עם מפת דרכים לשדרוג AIS.

**סטטוס:** Missing + External/ops risk | **עדיפות התחלה:** מיד אחרי/במקביל ליסוד הנה״ח (Phase 1b)

### 3.11 מסלול מקביל — Speed Insights P0 + זיכרון אנשי מקצוע (OPC)

**למה זה חלק מתוכנית 2.0:**  
מסכי Finance/דוחות/אמא־של־הבניין יהיו כבדים יותר — חייבים בסיס ביצועים יציב במובייל ודשבורד. במקביל, דירוג אנשי מקצוע הוא זיכרון תפעולי (השראת OPC) שמקצר זמן שיוך ומזין בהמשך **בחירת ספק להוצאות** ועלויות לבניין.

#### A) Speed Insights ישראל — P0 (PR1 נפרד, בלי schema)

| ממצא | כיוון תיקון |
|------|-------------|
| `/worker` CLS גבוה | AppShell: `useLayoutEffect` + CSS media למובייל; לא לכפות desktop לפני מדידה |
| `/dashboard` LCP חלש | פיצול shell: hero RSC + CTA זעיר; **לא** להסיר `ssr:false` מ־`dashboard-client` |
| Loaders מוחקים UI | Skeleton יציב (header/toolbar + רשימה) ב־`/worker` |
| Inter מיותר | הסרה מ־layout / fallback ל־Heebo |

**גבולות בטיחות:** אין נגיעה ב־middleware / tenant / session JWT. אחרי deploy — Bamakor smoke + בדיקת runtime errors.

#### B) זיכרון אנשי מקצוע מערכתי — (PR2 נפרד)

לא רק בדף `/professionals`, אלא בכל מקום שמנהל בוחר איש מקצוע (העברה מתקלה, drawers, המלצות):

- דירוג אישי 1–5 + הערה  
- מונה שימוש + תאריך מגע אחרון  
- מיון אחיד: דירוג → שימוש → רצנטיות  
- אחרי forward מוצלח — עדכון מונה שימוש  

**חיבור ל־Finance:** אותו מודל ישמש כבסיס לספקי הוצאות / עלות אמיתית לתקלה־בניין (true-cost) בשלבים מאוחרים.

#### C) Backlog השראת OPC (אחרי PR2)

## 5. החלטות שמבקשים מההנהלה עכשיו

1. **לאשר Phase 1** (הנהלת חשבונות + תקציב + מרכז פיננסי) כעדיפות עליונה ל־Finance.  
2. **לאשר פיילוט בנק** על בסיס `israeli-bank-scrapers` (MIT) עם feature flag, הצפנת סיסמאות, והבנה שזה שלב ביניים לפני AIS מורשה.  
3. **לאשר כיוון חתימות:** קישור לדיירים מתוך BINO (MVP) + אפשרות DocuSeal/OpenSign כשירות נפרד בהמשך; סף ברירת מחדל **רוב**.  
4. **לאשר מסלול מקביל:** PR1 Speed Insights P0 ואז PR2 זיכרון אנשי מקצוע (לפני/לצד UI Finance) — בלי לערבב עם שינויי auth.  
5. **לאשר** שאיסוף דוגמאות OPC מהלקוח הוא תנאי לעיצוב הדוחות.  
6. **למנות** גורם משפטי/חשבונאי לשאלת מנפיק קבלה/חשבונית (ועד / חברת ניהול / Grow) — BINO לא תוכרז מנפיקה אוטומטית לכל בניין.  
7. **לא לאשר עדיין** פתיחת חשבון בנק אוטומטית או ייזום תשלומים בנקאיים.
