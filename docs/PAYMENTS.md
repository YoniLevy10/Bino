# מודל הגבייה — מה קורה פה

מטרה אחת: **לקוחות הפלטפורמה (חברות ניהול) גובים כסף מהדיירים שלהם.**

במקור לא סולקת ולא מחזיקה כסף. אין «חשבון תשלומים של במקור».

```
דייר → קישור /pay → טופס Morning של הלקוח → כסף לחשבון Morning של הלקוח
במקור רק: יוצרת חיוב, שולחת SMS, מסמנת «שולם»
```

## למה Morning נשאר

הבחירה נכונה למודל הזה, גם אם ההפעלה מרגישה כבדה:

- כל לקוח כבר צריך חשבון סליקה משלו (Grow / Cardcom / ישראכרט). Morning הוא השכבה שמחברת חשבונית + קישור תשלום + סליקה.
- הכסף לא עובר דרך יזם הפלטפורמה — זה אילוץ מוצר, לא באג.
- החלפה ל-Cardcom/Grow ישירות = פרויקט חדש, בלי לקצר את ה-KYC של כל לקוח.

לא מחליפים ספק עכשיו. הבעיה הייתה זהות: עמוד Grow אחד של הפלטפורמה מול כסף שנכנס לחשבון של הלקוח.

## מי ממלא מה

| | יזם הפלטפורמה | הלקוח (למשל שרה) |
|---|---|---|
| בונה את המערכת / מביא לקוחות | כן | — |
| כסף מדיירים | **לא, בשום צורה** | חשבון Morning שלה |
| מפתחות API | `GREENINVOICE_WEBHOOK_SECRET` ב-Vercel | מפתח+סוד של **החשבון שלה** |
| עמוד Grow | לא רלוונטי לפיילוט שלה | `/vaad-pay/{clientId}` עם **השם/טלפון/כתובת שלה** |

`LEGAL_*` ב-Vercel הם רק לעמוד הפלטפורמה (`/vaad-pay`). Grow של הלקוח חייב לראות את **העסק שקולט את הכסף**.

## הפעלה (פיילוט)

1. להריץ `090_client_grow_legal.sql` ב-SQL Editor (087/089 כבר בפרודקשן; 088 IF NOT EXISTS).
2. `GREENINVOICE_WEBHOOK_SECRET` ב-Vercel.
3. סופר-אדמין: תוסף גבייה ללקוחה.
4. הלקוחה בהגדרות → Morning: מפתחות, בדיקת חיבור, פרטי עסק, העתקת שני קישורים ל-Morning (Webhook + עמוד Grow).
5. אחרי ש-Grow מוריד «ממתין לאישור»: חיוב ניסיון אחד → «שולם» + מייל קבלה.

בלי שלב 5 — לא מוכרים גבייה ללקוחה.
